### Ссылка на условие задачи / контеста

**Контекст:** На экране ревью преподаватель видит код посылки, но не может быстро открыть условие задачи. `EjudgeContestChip` (`scainer-front/src/features/ejudge/EjudgeContestChip.tsx`) умеет открывать контест в ejudge, но не конкретную задачу. В API `ProblemInfo` (`scainer/api/openapi.yaml`) есть только `id`, `name`, `submissionCount`, `pendingCount` — URL условия нет.

**Идея:** Добавить ссылку рядом с чипом задачи в хедере ревью (и/или в панели посылки). Варианты реализации:

- Собрать URL ejudge по шаблону (`ejudge.base_url` из конфига + contest/problem id)
- Или расширить API, если URL условия хранится/импортируется из ejudge

Затронутые файлы: `ReviewProblemPicker.tsx`, `ContestPage.tsx`, возможно бэкенд `contest_reader.go`.

### Кнопка Compare между посылками (по умолчанию — предыдущая по задаче)

**Контекст:** В ejudge есть встроенное сравнение посылок (см. `view_source_run_114_full.html` в тестах: поле `run_id2` + action Compare). В scAIner side-by-side есть только в детектах (`FindingCard.tsx` → `SideBySide`), на экране ревью — нет.

Посылки по задаче сортируются по времени в `submissionsForProblemReview` (`reviewFindings.ts`) — «предыдущая» = предшествующая в этой очереди (или предыдущая того же участника — уточнить при реализации).

**Идея:** Кнопка «Compare» в `ReviewSubmissionPanel.tsx`: открывает diff текущей посылки с предыдущей по задаче (inline side-by-side или ссылка в ejudge). Дефолтный `run_id2` — предыдущая посылка; опционально — выбор другой.

### Обновлять счётчик PR в чипе задачи после вердикта

**Контекст:** Счётчик в чипе — `review-picker__pr` в `ReviewProblemPicker`, считается через `prCountByProblem(submissions)` из кэша `getContestSubmissions`. После OK/RJ в `ReviewSubmissionPanel.submitVerdict` инвалидируется только `getSubmissionComments`, не список посылок — число в чипе не уменьшается до перезагрузки.

**Идея:** После успешного вердикта — `invalidateQueries` для `getContestSubmissions` (и/или optimistic update `verdict` в кэше). Учесть, что `ReviewPage` держит session queue и не убирает посылку из стека до смены задачи — счётчик в хедере и поведение стека должны быть согласованы.

### Фильтр PR по имени участника (подгруппы 6A / 6B)

**Можно ли сейчас?** Нет. Единственный фильтр на экране ревью — чекбокс **PR only** (`ReviewProblemPicker.tsx`, хук `useReviewPrOnlyFilter.ts`). Он отбирает посылки по `verdict ∈ {PR, PD}`, но не смотрит на участника. Счётчики PR в чипах задач (`prCountByProblem` в `reviewFindings.ts`) тоже считаются без фильтра по имени.

**Кейс:** В 6-й группе параллель разбита на подгруппы (6A, 6B); разные преподаватели проверяют «своих». В ejudge это решается фильтром вида `status == PR && name ~= ".*6B.*"`. В scAIner данные уже есть на клиенте: у каждой посылки поле `participant` (логин или отображаемое имя из ejudge, см. `mapParticipant` в `submission.go`) — фильтрация возможна целиком на фронте, без изменений API.

**Идея — легковесный и удобный фильтр:**

Рядом с «PR only» в `ReviewProblemPicker` добавить поле **«Участник»** (placeholder: `6B` или `.*6B.*`):

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Подстрока** (дефолт) | Просто, понятно преподам; `6B` → `participant.includes("6B")` | Не покрывает сложные паттерны |
| **Regex** (опционально, по префиксу `/…/`) | Совпадает с ejudge `name ~= "…"` | Ошибки в regex, сложнее UX |
| **Пресеты-чипы** (`6A`, `6B`, `Все`) | Один клик для типичного кейса | Нужна настройка под контест |

Рекомендация: **подстрока по умолчанию** + сохранение в `localStorage` (как у PR only) + применение единообразно в:

- очереди посылок (`submissionsForProblemReview`)
- счётчиках PR в чипах задач (`prCountByProblem`, `firstProblemWithPr`, `nextProblemWithPr`)
- пустых состояниях (`ReviewPage`)

Пустое поле = без фильтра по имени (все PR). Обновить легенду в `ReviewLegendModal`.

Бэкенд не обязателен; при больших контестах можно позже добавить query-параметр на API, но для MVP достаточно клиентской фильтрации по уже загруженному `getContestSubmissions`.

# Предварительные требования к системе детекции нечестных решений

> Статус: **черновик**. Помечай, с чем не согласен, что добавить/убрать — итеративно уточняем.
> Контекст: ЛКШ-подобная школа, задачи формата ICPC, 300+ участников.

## 0. Контекст и допущения

- **Домен:** летняя компьютерная школа, задачи в формате ICPC, 300+ участников, регулярные туры.
- **Источник данных:** ejudge, но система **не завязан**а на него — доступ к данным идёт через абстрактный интерфейс (адаптер).
- **Доступные данные (по факту, из judge):** исходный код посылки, язык, timestamp, вердикт, привязка к задаче/участнику/туру, последовательность посылок участника, возможно — компиляционные логи и результаты по тестам.
- **Недоступно:** машины участников → **нет** keystroke-логов, телеметрии IDE, прокторинга, записи экрана. Все поведенческие сигналы — только submission-level.
- **Режим:** гибрид — онлайн-сбор сигналов во время тура + основной анализ и вердикты после тура.



## 1. Функциональные требования



### 1.1. Приём данных и абстракция от judge

- **FR-1.1** Интерфейс `SubmissionSource`, скрывающий ejudge; реализации-адаптеры подключаемы (ejudge сейчас, другие позже).
- **FR-1.2** Импорт как batch (после тура), так и инкрементально/стримингово (во время тура — для гибридного режима).
- **FR-1.3** Нормализация в единую внутреннюю модель: `Submission {id, participant, problem, contest, lang, source, timestamp, verdict, tests, meta}`.
- **FR-1.4** Идемпотентность импорта (повторный импорт не плодит дубликаты, поддержка «дозагрузки»).



### 1.2. Модульный фреймворк детекторов (ядро)

- **FR-2.1** Единый интерфейс детектора — pluggable-модуль, дающий на выходе **сигнал подозрительности** (score + свидетельства/evidence + метаданные), а не бинарный вердикт.
- **FR-2.2** Детекторы независимы и включаются/отключаются/конфигурируются декларативно (на уровне тура/задачи).
- **FR-2.3** Три **области видимости** детектора должны быть first-class в архитектуре:
  - **Scope-A (изолированная посылка):** анализ одной посылки саму по себе (напр. AI-детектор, стилометрия, «слишком зрелый» код).
  - **Scope-B (cross-participant в рамках задачи):** сравнение посылок разных участников по одной задаче (плагиат: MOSS/JPlag-подобное).
  - **Scope-C (temporal / self-comparison):** сравнение соседних посылок одного участника — дрейф стиля, скачки сложности.
- **FR-2.4** Детектор объявляет требуемый scope и входные данные → планировщик формирует нужные наборы (пары, окна, одиночные посылки) и не гоняет лишнего.
- **FR-2.5** Возможность добавить новый детектор без изменения ядра (SDK/контракт + регистрация).



### 1.3. Конкретные семейства детекторов (набор наполним по итогам ресёрча)

- **FR-3.1 (Scope-B) Similarity:** структурное сравнение кода, устойчивое к переименованию/реструктуризации; кластеризация похожих групп, а не только пары.
- **FR-3.2 (Scope-A) AI-usage:** признаки LLM-генерации кода (стилометрия, «неестественная» зрелость, комментарии/идентификаторы, характерные паттерны).
- **FR-3.3 (Scope-C) Behavioral:** скачок качества/сложности между посылками, аномальные тайминги, «сразу-начисто» решения сложных задач.
- **FR-3.4** Учёт «нормальных» коллизий: шаблоны, стандартные алгоритмы, разрешённые сниппеты (whitelist/библиотека шаблонов) → снижение FP.



### 1.4. Агрегация и скоринг

- **FR-4.1** Слой **fusion**: объединение независимых сигналов в итоговую оценку подозрительности по (участник, задача) и по (пара участников, задача).
- **FR-4.2** Веса/пороги настраиваемы; стратегия объединения — сменный компонент (правила / взвешенная сумма / ML позже).
- **FR-4.3** Итог — **ранжированный список кейсов** для ревью, а не автоматическое наказание.
- **FR-4.4** Полная трассируемость: какой детектор какой вклад дал (объяснимость).



### 1.5. Разбор жюри (human-in-the-loop)

- **FR-5.1** UI/отчёт с ранжированными кейсами, side-by-side диффами кода, подсветкой совпадений, таймлайном посылок.
- **FR-5.2** Статусы кейса (новый / в разборе / подтверждён / отклонён / эскалация) и фиксация решения жюри с обоснованием.
- **FR-5.3** Экспорт отчёта по кейсу (для разговора с участником / апелляции).



### 1.6. Хранение свидетельств и аудит

- **FR-6.1** Неизменяемое хранение исходников, сигналов и решений (воспроизводимость на момент вердикта).
- **FR-6.2** Аудит-лог всех действий (кто, когда, что изменил).



### 1.7. Конфигурация и запуск

- **FR-7.1** Профили анализа на уровне тура/задачи (какие детекторы, пороги, whitelist).
- **FR-7.2** Ручной и автоматический (по завершении тура) запуск анализа; онлайн-сбор во время тура.



## 2. Нефункциональные требования

- **NFR-1 Масштабируемость:** Scope-B — это потенциально O(n²) сравнений на задачу (300+ участников × десятки задач × туры). Нужна предфильтрация (fingerprint-индекс, LSH/MinHash) до дорогих попарных сравнений; горизонтальное распараллеливание.
- **NFR-2 Производительность:** результаты по туру — в разумное окно после его завершения (целевой SLA определим совместно, напр. «≤ N минут после конца тура»).
- **NFR-3 Точность и управление FP:** приоритет — **низкий false positive** (обвинять школьника ошибочно недопустимо); система лишь ранжирует, финальное слово за человеком.
- **NFR-4 Объяснимость:** каждый сигнал сопровождается человекочитаемым свидетельством; «чёрный ящик» без обоснования неприемлем.
- **NFR-5 Справедливость / due process:** воспроизводимость вердикта, право на апелляцию, отсутствие автоматических санкций.
- **NFR-6 Приватность (несовершеннолетние):** минимизация данных, ограниченный доступ, политика хранения/удаления, шифрование чувствительных данных.
- **NFR-7 Расширяемость:** добавление детектора/адаптера/стратегии fusion без переписывания ядра (плагинность как архитектурный инвариант).
- **NFR-8 Надёжность/идемпотентность:** повторный прогон даёт тот же результат; сбой одного детектора не роняет анализ.
- **NFR-9 Наблюдаемость:** метрики покрытия, времени прогона, распределения score; логирование.
- **NFR-10 Портируемость:** независимость от конкретной judge-системы и, желательно, от конкретной СУБД/очереди на уровне интерфейсов.



## 3. Вопросы для уточнения (перед проектированием архитектуры)

1. Есть ли доступ к **компиляционным логам / результатам по тестам** и к **промежуточным** (не только финальным) посылкам? Это сильно влияет на Scope-C.
2. Языки участников (C++/Python/Java…?) — от этого зависит выбор парсеров/токенизаторов.
3. Нужно ли сравнивать с **внешними/архивными** решениями (прошлые годы, интернет), или пока только внутри тура?
4. Кто и как разбирает кейсы (число членов жюри, ожидаемый объём ручного ревью)?
5. Технологические ограничения (стек, on-prem vs облако, бюджет на внешние сервисы вроде API LLM-детекторов)?
